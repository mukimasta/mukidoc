# OVERVIEW Design

OVERVIEW lets someone encountering the project for the first time quickly build a complete outside-in picture. It answers what the project is, what problem it solves, what it will deliver, and how users will actually use it, without going into internal design, architecture and implementation.

The structure of the whole text is fixed:

**Project definition → The problem → Deliverables → User scenario → Closing line**

Open by defining the project directly, with no subheading. In a short paragraph state what the project is, who it is for, and its core role.

**The problem.** State the real-world problem and the user predicament the project addresses, answering why this project is needed. Stay at the problem level; do not go on to ask about the essence of the problem or expand into design philosophy. One paragraph is recommended.

**Deliverables.** State clearly what the project ultimately provides to users as results they can obtain, use or hand off directly. Focus on externally visible products and do not expand on how they are implemented inside. When there are many, a short list may be used.

**User scenario.** Use one concrete, continuous, typical scenario to describe how a user actually uses the project. The scenario should have a natural start, a process of use and an outcome, letting the reader directly imagine "what it will be like after using it", rather than listing the features again. One paragraph is recommended; two scenarios may be used when necessary.

Finally close with one sentence that describes, from the standpoint of results, the ideal state the project can bring to users: "paint the picture", talking about how much simpler, smoother or more powerful things that used to be hard become after using this.

Keep the whole text short, in principle no more than 800 words. A good OVERVIEW lets someone who knows nothing about the project learn within a few minutes: what this is, why it is worth using, how to actually use it, and what they finally get.
