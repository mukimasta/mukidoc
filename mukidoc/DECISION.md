# Decision

1. Do not adopt arc42 as the top-level documentation system. It examines the same Architecture from multiple angles, so adopting it is almost the default answer, whereas MukiDoc unfolds downward from Design to Implementation. In the end we keep our own structure and borrow only the useful concepts, at the cost of no longer reusing arc42's templates and toolchain.

2. Split the two layers Design / Implementation into three. Two layers is the most natural default division for design documents, but the boundary kept blurring when discussing Database: a database model looked like an implementation of the upper-level Design, and also like the Design of the lower-level code. After working through login and a bookstore, a standalone, ever-present question surfaced in the middle: "to implement this design, how should the internal system be organized and run?" We finally separated out System Design, and accepted that "lower-level Design is also higher-level Implementation." The cost is that deciding the layer requires human judgment, and the number of documents grows.

3. Keep ROADMAP static and leave actual development history to DEVLOG. ROADMAP originally described "what has been done, where we are now, and what comes next," which is the default understanding of a roadmap in most projects, but then it changes with every day of development and easily degrades into a progress table. In the end it describes only how capability and maturity evolve, and how things actually went is left to a time-ordered, append-only record of the development thread. It cannot be called IMPLEMENTATION.md: implementation/ is already a formal concept in the design chain, and the duplicate name would keep creating ambiguity. The cost is that ROADMAP no longer answers "how far along are we."

4. Evaluation arises from the commitments of every layer from PHILOSOPHY to Implementation, and is not equivalent to Tests. In discussion it is easy to slide into format checks, unit tests and performance tests and treat them as synonyms, which is a very natural default understanding, but these only show certain properties of an implementation. The real standard comes from PHILOSOPHY: whether a new Agent can take over the project, whether humans can control the system mainly through documents, whether the three layers are truly decoupled. "Which layer's commitments are evaluated" and "at what Scope to test" are two orthogonal dimensions, and every MukiDoc project also ships with an Evaluation aimed at the documentation system itself. The cost is that each layer's commitments must be defined separately.

5. AGENTS.md takes a "compilation" approach, rather than copying the full specification or prescribing a workflow. At first we considered having it teach the Agent what to read first, what to do next, and which Designs to load on demand, but that would become a rigid workflow and underestimate the judgment of strong models. In the end the detailed Design is treated as source code and AGENTS.md as the dense compiled output: it keeps only the project map, semantic boundaries and key rules that affect judgment, and drops derivations, explanations and most examples; it prescribes no fixed Runtime and only constrains relationships that must not be broken. It is organized as Role, MukiDoc, Design, Develop, Evaluate, and lives in the repository root. The cost is that it must be recompiled when the Design changes, and the two can drift apart.

6. Information sits alongside Project Context and does not belong to it. "Project Context" is a scope term, and "everything at the project level" naturally reads as including Information; that is how the repository understood it, and its Design always lived under design/project_context/. But by that standard, project-level content in Evaluation and the Design Chain would also have to come in, and in the end this region would distinguish nothing. So the two are divided by nature rather than scope: Project Context is the project's own formal narrative, and Information is the materials and evidence on which those narratives rest. The criterion is whether something has entered the formal narrative, regardless of time: DEVLOG and investigations both tell what happened, but one goes into the main line and the other is merely evidence. As a result, "project-level context" in ARCHITECTURE needs tightening to "the authoritative description of the project itself."

7. Organize the inside of the Design Chain by Area, rather than mirroring by layer or laying things flat by feel. The defaults are either to have the three layers each mirror a same-named directory per feature, or simply to lay everything flat; the former produces many empty directories, and the latter, once documents multiply, becomes a pile of self-governing files. After working it through, the second dimension was settled as Area, the problem space a project forms naturally, and defined as "fixed Layer, free Area": the three layers are constant vertically, Areas are free horizontally, with no mirroring, growth on demand, and cross-cutting concerns at the layer root. The cost is that dividing Areas requires human judgment, and the structure of the layers is no longer symmetric.

8. The Chinese version is the single source, and the English version is only a translation. When open-sourcing, the most natural approach is to maintain one bilingual repository, or let the two languages evolve separately; the former requires every document to be maintained twice, and the latter soon forks. In the end the Chinese repository `mukidoc-zh` is the single source, where daily thinking and iteration happen; the English repository `mukidoc` is the public main repository, synchronized as a whole translation only after the Chinese version is released, never edited directly for content, with each sync noting the corresponding Chinese version and commit in its commit message. The cost is that the English version will always lag the Chinese version for some time.

9. The documentation root is `mukidoc/`, not `docs/`. `docs/` is the most natural default and was the original choice, but it already has a fixed meaning across the ecosystem: user-facing documentation, the default for GitHub Pages, MkDocs and Sphinx. MukiDoc holds the project's long-term context; once it claims `docs/`, the project's own documentation, articles or docs site must take an awkward alternative name, every project has to explain this again, and bringing an existing project into MukiDoc collides directly with its existing `docs/`. A dedicated name lets an Agent recognize the protocol at a glance and gives `docs/` back to the project. The cost is a name less obvious than `docs/`, so first-time visitors need the README to point the way.
